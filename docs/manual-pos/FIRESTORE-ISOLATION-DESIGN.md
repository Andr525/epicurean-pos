## S1 — PIN verification and staff sessions

PIN login is a backend operation, not searching STATE.staff and assigning a role. Synthetic staff fixture has immutable staffId, active status, role, restaurant/run scope and PIN verifier. Client supplies PIN and terminal/session challenge, never role/grant/staff identity as authority. Verification returns an opaque random256-bit session ID associated server-side with staffId, policy revision, terminalId, runId, issuedAt, idle/max expiry and revocation generation. Auth-emulator tokens alone are not trusted staff sessions: emulator tokens can be forged in test conditions; backend must require its own issued session and current fixture policy.

Idle expiry15min, absolute expiry60min or earlier owner expiry. Every read/mutation rechecks session and current active/grant generation. Logout/relogin/switch staff revokes the old session and in-flight approvals, rejects replies from older generation and clears browser secrets; pending draft remains durable data, not authorization. Reload reacquires session validation before opening a check. Cookie is HttpOnly/SameSiteStrict; full PIN-bearing phone testing requires separately approved HTTPS and Secure cookie, not the present private-Wi-Fi HTTP screen profile. Current HTTP profile remains synthetic/no-backend/no-manager-authority. Rate-limit invalid PIN attempts per terminal/staff/global, return uniform errors and never log PIN/session secrets. No real staff PIN may enter the local harness.

## S2 — Manager-code security and one-use approvals

Server resolves an active manager from a synthetic fixture verifier, not client managerName/role. Hash codes using Argon2id (proposed memory64MiB,time3,parallel1,salt16bytes) with a server-only random32byte pepper; verify library/config compatibility before build. Verifiers/pepper stay outside repository/browser/audit and cannot be read through emulator client rules. Short PIN entropy is not solved by hashing: enforce trusted test terminal binding plus per-manager/per-terminal/global lockout (five invalid attempts in15min), persisted across backend restarts; unknown manager and bad code have identical responses. This is test security, not a claim that production4digit codes are adequate without separate threat review.

A fresh successful code entry authorizes ONE specified void/comp/discount. It is required even when initiator is already a manager. Approval expires in60sec or sooner on logout/revocation/check change; binds managerId, initiatorId, session generation, terminal/run, action, check/line IDs, expected check/catalog/allergy revisions, reason and canonical amount/intent digest. Approval consumption, adjustment, audit and idempotent result occur in one transaction. Same requestId+digest returns same result; altered body or another request cannot reuse the approval. Denial consumes no approval and changes no financial/state documents. Separate failure-attempt security events contain no codes/verifiers.

## S3 — Exact-position and allergy/substitution data

Authoritative service session: serviceSessionId, tableId, revision, positions[{positionId, exactLabel:'2'|'2A'|'3', active}], tableAllergens[], allergiesByPositionId, allergyRevision, notesByPositionId, substitutionsByPositionId and explicit legacy-migration state. Position IDs are stable; numeric seat/suffix is display compatibility only. Each check references its service session; each line has checkId, stable lineId, positionId/exactLabel snapshot, course/menu/selection IDs and immutable BOH price/allergen snapshots. Split/transfer does not relabel a guest or duplicate allergy authority; it updates scoped references transactionally.

Queries/permissions/notes use exact registered IDs; no parseInt fallback for identifying a guest. Persist AND restore table/position allergies, substitutions, free notes and relevant revisions, not just guest display rows. Kitchen intent includes exact position and scoped allergy/note snapshot; a flattened list of allergens cannot replace per-position evidence. On new allergy revision after SEND, record the change durably, invalidate stale pending confirmations/FIRE, create a local safety-notification intent for already accepted affected orders, show unresolved warning until acknowledged, and retain fired history. Never pretend accepted food was unsent. Allergy-override authority remains BLOCKED until owner policy is explicit.

Migration is versioned and approved, never guessed. A legacy numeric2 key with only an A label may be read conservatively under legacy schema; converting to explicit2 AND2A is ambiguous. Quarantine affected mutations, retain original records and require an explicit approved mapping with before/after audit. Do not silently copy/drop2 restrictions or substitutions. Present C2/C3 code does not implement this contract.

## S4 — Network and credential isolation

Use demo-epicurean-manual only; exact Firestore127.0.0.1:8080/Auth127.0.0.1:9099/backend127.0.0.1:9444, within a dedicated test network namespace/container. All emulator/API/browser test processes share that namespace; runtime outbound network disabled at OS/container boundary except its loopback. No production SDK/default-credential lookup, GOOGLE_APPLICATION_CREDENTIALS, service-account mount or real project configuration. Refuse startup on non-demo ID, wrong host, credentials, absent emulator, failed health check or inability to establish isolation. No fallback to live endpoints.

Preparation/downloads are a separate approved step with published artifact integrity checks, never runtime egress. Tests must demonstrate an actual outbound connection is denied; CSP/host strings alone are insufficient. Expose no Auth/Firestore/sink ports to the LAN. Current physical HTTP screen profile is a separate no-backend path, not a privileged proxy. A future iPhone write/manager/session profile requires new network/TLS review and owner authorization. Authenticated browser integration in the namespace requires an independently verified test-only HTTPS/trust configuration; do not use ignoreHTTPSErrors, certificate-error switches or personal trust-store changes to get green tests. If the runner cannot enforce these constraints, stop/BLOCK rather than weaken them.

## S5 — Kitchen intents, acknowledgments and late allergies

No real device/printer/queue exists. Backend atomically creates a unique intent with run/check/line/position/course, actor/grant revision, payload digest, catalog/allergy/check revision, authorization/override reference and pending state. A LOCAL sink durably records receipt keyed by intentId+digest BEFORE issuing an authenticated acknowledgment (server-only test key, never browser posted ack authority). Duplicate same intent returns the original receipt; digest mismatch is rejected. No final sent/fired flag before accepted acknowledgment. Worker crash/retry cannot create a second sink effect.

ACK transaction validates exact intent identity/digest, current state, actor authorization and relevant allergy changes. Failure/timeout stays pending/failed with visible evidence; forged/stale/reordered acknowledgments do not change state. Crash after receipt but before local state commit recovers by querying/retrying the same durable intent. Positive/duplicate/failure/drop/delay/reordered/revoked-grant/late-allergy cases all have fixture tests. Do not claim real-world exactly-once delivery from this recording sink. Fired history is append-only; void is a separately approved reversal intent. Owner grants server/manager SEND+FIRE; kitchen only explicitly granted FIRE, never SEND. FIRE revalidates actual course and allergy revision, never only button visibility.

## S6 — Durable reload/offline/crash recovery

A committed response means check, structured lines, exact allergy/substitution data, approval consumption, audit and request result are durable in one local transaction. Reload fetches that schema and verifies revisions, not reconstruction from names/selectedMod or STATE memory. Test backend restart, page close/reopen, process kill before/after commit, two clients, revoked sessions and pending sink ACK recovery. C2 roundtrip is an explicit failing baseline until it passes through this approved durable adapter.

Use a durable client operation journal only for synthetic run data: pending requestId, stable draft/line operationId, canonical digest and expected revision. Never persist PIN, pepper, manager code or reusable approval secret. No final mutation can be acknowledged offline; show pending/BLOCKED. On reconnect, reconcile request status before retrying identical ID, never create a fresh duplicate. Revalidate expired authorization/manager approval for uncommitted requests; preserve drafts without pretending approved authority survived logout. Fresh run directories are temporary; same-run restart must preserve data until reconciliation, then teardown explicitly. No “restart resets fixtures” masquerading as durable recovery.

## S7 — Concurrency, replay and rapid double-tap

Every mutation carries expected check/service/allergy version and stable operationId. Read these in the transaction with active session/role/grant, not a stale cached client context. Conflict returns explicit current version and no mutation; client must review before resubmission. A requestId is unique within run and actor/session, body digest immutable. Replays across staff, check, item, run, logout generation, expiry, action or altered discount/reason are denied; same valid finalized request returns immutable result/audit.

Pending Add/Confirm/SEND/FIRE/adjustment owns a single operationId created when the draft/action begins. Rapid multiple UI events while that operation is pending share its ID and cannot create a second line/menu/intent. Disabling buttons is usability, not protection: direct API duplicate calls must be idempotent and database uniqueness enforced. Legitimate later quantity/add actions get new reviewed operationIds; do not deduplicate merely by matching a dish name. Test two concurrent transactions, duplicate different requestIds bound to the same pending operation, timeout retry, altered-payload replay, approval reuse and concurrent void/comp/discount.

## S8 — Financial authority, tax and tip calculations

All prices/options/taxability come from a pinned authentic catalog/config revision. Preserve original BOH prices; derive net amounts from authorized adjustment records. Missing price/taxability or unsupported modifier is BLOCKED, not zero/free/inferred. Numeric ID text and “$” modifier text are not a price source. Validate positive integer quantity/defined pour model and cents precision; backend ignores client totals/role/manager identity. Zero/negative/malformed values and adjustment overflow are rejected.

Proposed reviewed math contract: NYCtax rate8875/100000 on approved net taxable cents, rounded half-up once at check level; line/check discount percentage rounding explicitly scoped before taxable aggregation. Full owner-approved comp/void gives zero chargeable base under the proposed merchant-funded adjustment policy, retaining source price/history. Third-party/exempt/tax-treatment unknowns block acceptance until approved; no ad-hoc taxability fields are fabricated. Deterministic largest-remainder split allocation conserves net/tax/tip/final cents across all checks; no double application on retry.

Tip basis is final check total INCLUDING tax after adjustments, choices20/25/40/Custom. Strict minimum ceil(totalCents*20/100); proposed preset20 uses that minimum,25/40 half-up and not below it. Custom is validated at the boundary and revalidated/reconfirmed after every adjustment/tax/split change. Separate subtotal, adjustments/net, taxable base, tax, tip and final display. Actual89.00 BOH PF arithmetic oracle: tax7.90,check96.90,tip19.38,final116.28; approved10% merchant discount example net80.10,tax7.11,check87.21,min-tip17.45,final104.66. These are reviewable financial vectors, not new menu prices or an implemented billing engine. Mandatory customer-menu disclaimer is a critical test on EVERY guest-menu surface.

## S9 — Collections, transaction permissions and audit contract

Candidate collections: catalog_revisions/{hash}, service_sessions/{id}, staff_policy/{id}, server_sessions/{opaqueId}, checks/{id}, check_lines/{id}, action_requests/{id}, manager_approvals/{id}, audit_events/{id}, kitchen_intents/{id}, kitchen_receipts/{id}. Version each schema. Server sessions and code verifiers are inaccessible to clients. No direct client write to checks/lines/roles/grants/approvals/audit/outbox; local backend is the sole transition writer. Emulator Rules test denial and scoped read access; server privileged SDK bypasses Rules, so API transaction checks are separately tested.

Audit event: immutable eventId/runId/serverTime, initiating staff and manager approval identity (where required), action, check/line/position, reason, expected/committed revision, before/after financial amounts and authorization/catalog/allergy references. No PIN/hash/session secret, no unapproved free-form private data. Atomic successful action produces exactly one audit; denied action zero financial/state changes plus separate sanitized security event. Sent-item void retains original item/sent/fired events and acknowledgement link. Test attempts to amend/delete audits, spoof actor/manager, reuse codes/approval, bypass API or import wrong-run data. Admin seeder only initializes hashed synthetic policies/catalog snapshots; it cannot be exposed as a POS route.
